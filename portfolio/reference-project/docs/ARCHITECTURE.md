# Enterprise Architecture and Threat Model

This document outlines the architectural specifications, component boundaries, and security model for the Enterprise Ticket Intelligence and Grounded Synthesis Engine (ETISE).

## Component architecture

ETISE is organized into four decoupled subsystems to ensure strict separation between data ingestion, model processing, operational storage, and human oversight.

### 1. Ingestion and normalizer subsystem

- Gateway: FastAPI application with client authentication, rate limiting, and request correlation IDs.
- Idempotency guard: verifies incoming `Idempotency-Key` headers against an in-memory TTL store (or Redis in clustered mode). Identical payloads within a 24-hour window return the cached response immediately, avoiding redundant model inferences and preventing duplicate ticket creation.
- Payload validator: enforces schema compliance using Pydantic models before data enters any queue or storage subsystem. Malformed payloads are rejected at the edge with HTTP 422 and a structured diagnostic report.

### 2. Extraction and repair subsystem

- Extraction pipeline: maps free-text email or ticket content into a strongly typed `TicketRecord`.
- Validation and self-correction: if the model returns schema errors (e.g. missing required fields, invalid enum strings), the error messages are aggregated and fed back into an automated repair loop.
- Refusal behavior: if the ticket lacks sufficient information to determine the defect category or urgency, the model is instructed to emit an explicit refusal signal rather than hallucinating plausible values.

### 3. Knowledge retrieval and grounding subsystem

- Knowledge store: indexed regulatory manuals, service level agreements (SLAs), and standard operating procedures (SOPs).
- Hybrid search: combines BM25 sparse keyword matching with dense embedding semantic search to ensure exact policy numbers (e.g. "Section 4.2.1") and conceptual queries are both retrieved accurately.
- Grounding verification: answers generated by the system must include verbatim quotations from the retrieved chunks. A deterministic validator verifies that each cited quotation appears verbatim in the source documents before presenting the answer to the user.

### 4. Human-in-the-loop (HITL) exception subsystem

- Exception queue: all tickets flagged with confidence scores below 0.85, high urgency (P0), or ungrounded citations are routed to an operator review queue.
- Override feedback: when a human operator reviews and corrects a ticket classification, the diff between the model prediction and the human decision is recorded in an append-only feedback ledger. This ledger forms the foundation for automated regression test expansion.

## Security and threat model

### Data boundaries and isolation

- Customer data boundary: all customer ticket payloads, email strings, and customer account identifiers remain within the designated environment boundary. No data is shared across tenant workspaces.
- Zero data retention: external LLM API configurations enforce zero data retention (ZDR) flags to prevent enterprise data from being used for foundation model training.
- Secrets hygiene: zero secrets or API tokens are committed to source control. Configuration is loaded strictly from environment variables via Pydantic Settings.

### Threat vectors and mitigations

- Prompt injection: customer tickets containing instructions to ignore previous system prompts or reveal internal guidelines are mitigated through strict input delimitation, structured JSON schema output forcing, and deterministic citation verification.
- Denial of service via payload amplification: requests are bounded by maximum payload size limits (2MB ceiling) and strict token count budgets.
- PII leakage in telemetry: logging layers sanitize sensitive fields (email addresses, phone numbers, payment account numbers) before exporting trace spans to observability aggregators.
